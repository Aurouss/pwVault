## 3. 技术栈

版本号不在本文写死，M0 阶段选定当时的稳定版并用 `package-lock.json` 锁定。

| 层 | 选型 | 用途 |
| --- | --- | --- |
| 运行时 | Electron | 桌面外壳 |
| 语言 | TypeScript（strict 模式） | 主进程、预加载、界面全部使用 |
| 工程脚手架 | electron-vite | 三端构建与开发热更新 |
| 界面 | Vue 3 + Pinia + Naive UI | 组件与状态管理 |
| Markdown 编辑 | CodeMirror 6 | 源码编辑器 |
| Markdown 渲染 | markdown-it + DOMPurify + highlight.js | 渲染、净化、代码高亮 |
| 加密数据库 | better-sqlite3-multiple-ciphers（SQLCipher 模式） | 整库加密的 SQLite，自带 FTS5 |
| 密钥派生 | Argon2id，实现库在 M0 从 `@node-rs/argon2` 与 `hash-wasm` 中选定 | 登录密码 → 密钥 |
| 对称加密、HKDF、随机数 | Node 内置 `node:crypto` | AES-256-GCM、HKDF-SHA256 |
| 设备绑定 | Electron `safeStorage`（Windows 上即 DPAPI） | 保护设备密钥 |
| 入参校验 | zod | IPC 契约 |
| 打包 | electron-builder | `nsis` 安装包；v1.1 增加 `portable` |
| 更新 | electron-updater | GitHub 源；v1.1 增加通用静态源（Nginx） |
| 测试 | Vitest、Playwright（Electron 模式） | 单元测试、端到端测试 |
| 规范 | ESLint + Prettier | — |

原生模块只有加密数据库一个（Argon2 若选 `hash-wasm` 则是 WASM，不算原生模块）。它必须有与所选 Electron 版本匹配的预编译包，这是 M0 的第一项验证。

## 5. 进程模型与职责

| 进程 | 信任级别 | 能做什么 | 不能做什么 |
| --- | --- | --- | --- |
| 主进程 | 可信 | 密钥运算、读写数据库和文件、剪贴板、更新 | — |
| 预加载脚本 | 受限 | 把固定的一组函数暴露给界面 | 不暴露通用的“调用任意通道”能力 |
| 界面进程 | 不可信 | 展示与交互，通过白名单函数请求主进程 | 访问 Node、文件系统、密钥、数据库 |

窗口创建时的固定配置：`contextIsolation: true`、`sandbox: true`、`nodeIntegration: false`、`webSecurity: true`；拦截 `will-navigate` 与 `setWindowOpenHandler`；拒绝全部权限请求；内容安全策略 `default-src 'self'; img-src 'self' blob: data:; style-src 'self' 'unsafe-inline'; object-src 'none'`；正式版不可打开开发者工具；`setContentProtection(true)` 受“禁止截屏”设置控制。

## 6. IPC 接口

### 6.1 规则

1. 全部使用 `invoke` / `handle` 请求-响应模式；主进程到界面的推送只有状态事件（锁定、更新进度）。
2. 每个处理函数第一步用 zod 校验入参，第二步检查会话状态。标注“公开”的接口未解锁也可调用，其余一律要求已解锁。
3. 校验调用来源必须是应用自身页面。
4. 错误以错误码返回，不把堆栈和内部路径传给界面。
5. 密码类字段的明文只通过 `entry:revealField` 单独下发；复制走 `entry:copyField`，由主进程写剪贴板。

## 7. 数据库设计

### 7.1 打开方式

```sql
-- 以 SQLCipher 模式、原始密钥方式打开（跳过库内置的口令派生），具体写法以所选库的文档为准
PRAGMA key = "x'<K_db 的 64 位十六进制>'";
PRAGMA journal_mode = DELETE;   -- 单文件，便于“退出后拷贝文件夹”
PRAGMA synchronous = FULL;
PRAGMA foreign_keys = ON;
PRAGMA secure_delete = ON;
SELECT count(*) FROM sqlite_master;  -- 触发一次解密校验，失败即密钥错误
```

选择 `DELETE` 日志模式而不是 WAL：数据量小，性能无差别；而 WAL 会在目录里多出两个伴生文件，增加“拷贝到一半不一致”的可能。

### 7.2 建表语句（数据格式 v1）

```sql
PRAGMA user_version = 1;

-- 键值元数据：vault_id、数据密钥副本、数据密钥确认时间、安全类设置
CREATE TABLE meta (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);

-- 级联目录
CREATE TABLE folder (
  id         TEXT PRIMARY KEY,                       -- UUID
  parent_id  TEXT REFERENCES folder(id),             -- NULL 表示根级
  name       TEXT NOT NULL,
  sort       INTEGER NOT NULL DEFAULT 0,
  created_at INTEGER NOT NULL,                       -- Unix 毫秒
  updated_at INTEGER NOT NULL
);
CREATE UNIQUE INDEX ux_folder_sibling ON folder (ifnull(parent_id, ''), name);

-- 分类：内置四种 + 自定义
CREATE TABLE category (
  id       TEXT PRIMARY KEY,
  name     TEXT NOT NULL UNIQUE,
  kind     TEXT NOT NULL CHECK (kind IN ('item', 'doc')),   -- doc = 纯 Markdown 文档
  color    TEXT NOT NULL,
  icon     TEXT NOT NULL,
  builtin  INTEGER NOT NULL DEFAULT 0,
  template TEXT NOT NULL DEFAULT '[]',               -- JSON：默认字段 [{label, kind}]
  sort     INTEGER NOT NULL DEFAULT 0
);

-- 条目（含 Markdown 文档）
CREATE TABLE entry (
  id           TEXT PRIMARY KEY,
  folder_id    TEXT REFERENCES folder(id),           -- NULL 表示根级
  category_id  TEXT NOT NULL REFERENCES category(id),
  title        TEXT NOT NULL,
  notes_md     TEXT NOT NULL DEFAULT '',             -- 条目备注，或文档正文
  favorite     INTEGER NOT NULL DEFAULT 0,
  sort         INTEGER NOT NULL DEFAULT 0,
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL,
  last_used_at INTEGER,
  deleted_at   INTEGER,                              -- 非空 = 在回收站
  origin_folder_id TEXT                              -- 进回收站前所在目录，供恢复
);
CREATE INDEX ix_entry_folder   ON entry (folder_id)   WHERE deleted_at IS NULL;
CREATE INDEX ix_entry_category ON entry (category_id) WHERE deleted_at IS NULL;

-- 字段
CREATE TABLE field (
  id       TEXT PRIMARY KEY,
  entry_id TEXT NOT NULL REFERENCES entry(id) ON DELETE CASCADE,
  label    TEXT NOT NULL,
  kind     TEXT NOT NULL CHECK (kind IN ('text', 'secret', 'url', 'multiline')),
  value    TEXT NOT NULL DEFAULT '',
  sort     INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX ix_field_entry ON field (entry_id);

-- 标签
CREATE TABLE tag (
  id   INTEGER PRIMARY KEY,
  name TEXT NOT NULL UNIQUE
);
CREATE TABLE entry_tag (
  entry_id TEXT    NOT NULL REFERENCES entry(id) ON DELETE CASCADE,
  tag_id   INTEGER NOT NULL REFERENCES tag(id)   ON DELETE CASCADE,
  PRIMARY KEY (entry_id, tag_id)
);

-- Markdown 内嵌图片
CREATE TABLE attachment (
  id         TEXT PRIMARY KEY,
  entry_id   TEXT NOT NULL REFERENCES entry(id) ON DELETE CASCADE,
  name       TEXT NOT NULL,
  mime       TEXT NOT NULL,
  size       INTEGER NOT NULL,
  data       BLOB NOT NULL,
  created_at INTEGER NOT NULL
);

-- 检索索引（在加密库内）。不含 secret 字段。
CREATE VIRTUAL TABLE entry_fts USING fts5 (
  entry_id UNINDEXED,
  title,
  fields,      -- 非密码字段的“字段名 值”拼接
  tags,
  path,        -- 目录路径
  body,        -- Markdown 正文
  tokenize = 'trigram'
);
```

### 7.3 数据格式升级

- 版本号记录在 `PRAGMA user_version`，升级脚本放在 `migrations/`，按编号顺序在单个事务内执行。
- 执行前先做一次备份（见 8.6）。
- 程序支持的最高版本低于库的版本时，拒绝打开并提示升级程序。
- `keystore.json` 有独立的 `format` 字段，规则相同。

## 8. 关键实现要点

### 8.1 密钥运算

```text
初始化
  MK       = random(32)                 主密钥
  K_dev    = random(32)                 设备密钥，经 safeStorage 加密后写入 keystore
  dataKey  = random(32)                 数据密钥
  vaultId  = uuid()

密码槽
  K_pwd  = Argon2id(password, saltP, m = 64 MiB, t = 3, p = 4) → 32 字节
  KEK_P  = HKDF-SHA256(ikm = K_pwd ‖ K_dev, salt = saltP, info = "pwvault/v1/slot-password")
  wrapP  = AES-256-GCM.seal(key = KEK_P, nonce = random(12), plaintext = MK, aad = header)

数据密钥槽
  KEK_D  = HKDF-SHA256(ikm = dataKey, salt = saltD, info = "pwvault/v1/slot-datakey")
  wrapD  = AES-256-GCM.seal(key = KEK_D, nonce = random(12), plaintext = MK, aad = header)

数据库密钥
  K_db   = HKDF-SHA256(ikm = MK, salt = vaultId, info = "pwvault/v1/db")

header = { format, vaultId, 槽名, kdf 参数 } 的规范化 JSON
```

- 每次重建某个槽都换新的盐，所以每个 KEK 只加密一次，不存在随机数重复使用的问题。
- 密钥材料全部放在 `Buffer` 里，锁定时 `fill(0)`。登录密码在 JavaScript 中是字符串，无法可靠清零，这是已知局限，处理方式是尽快转成 `Buffer` 并缩短其存活范围。
- `safeStorage` 在 Windows 上的实现是：生成一把密钥，用 DPAPI 保护后存在应用数据目录的 `Local State` 文件里。因此清空应用数据目录等同于更换设备，需要数据密钥恢复。这一点在 M0 实测确认。

### 8.2 数据密钥的编码

```text
payload = dataKey(32 字节) ‖ CRC-16(dataKey)(2 字节)       共 34 字节
文本    = Crockford Base32(payload)                       55 个字符，每 5 个一组，共 11 组
```

解码时去掉空格和连字符、转大写，并按 Crockford 规则把 `I`、`L` 视为 `1`，把 `O` 视为 `0`，最后校验 CRC。输入界面在每组填满后即时提示格式是否正确。

### 8.3 检索

- `entry_fts` 由应用代码维护：`entry:save`、移动、删除、恢复时在**同一事务**内更新对应行（字段和标签来自多张表，不适合用触发器）。
- 查询词按空白切分，每个词都必须命中：
  - 长度 ≥ 3 的词走 `MATCH`，词用双引号包裹并转义，避免被当作查询语法；
  - 长度 1–2 的词（如“密码”）走同一张表上的 `LIKE '%词%'`，全表扫描，在本工具的数据规模下可以接受。
- 排序：用 `bm25` 的列权重实现，标题 10、字段与标签 5、目录路径 2、正文 1。
- 命中片段用 `snippet()` 生成，高亮标记由界面转成 `<mark>`，转换前先做 HTML 转义。
- 结果关联 `entry` 表，排除回收站中的条目。

### 8.4 Markdown 导出

- 条目 → Front Matter + 一级标题 + 字段表格 + “备注”章节；文档 → Front Matter + 正文。
- 表格单元格内的 `|` 转义，换行替换为 `<br>`；“多行文本”类型的字段不放进表格，改为表格下方的围栏代码块，围栏长度根据内容自动加长。
- 正文中的图片在库内写作 `![说明](attachment://<id>)`，导出时把图片写到 `assets/` 并改写为相对路径。
- 文件名处理：替换 `\ / : * ? " < > |` 和结尾的点、空格；规避 `CON`、`NUL` 等保留名；同目录重名追加 ` (2)`。
- 先写到临时目录，全部成功后再移动到目标位置；选择 zip 时在临时目录内打包。
- 明文导出必须通过一次 `auth` 校验（重新输入登录密码）。

### 8.5 数据导入（迁移）

1. `migrate:inspect`：检查 `keystore.json` 可解析且格式版本受支持、`vault.db` 存在；尝试用本机 `safeStorage` 解开设备密钥，失败则标记为“来自其他设备”。
2. `migrate:import`：
   1. 把源文件夹复制到 `<数据目录>.importing`，此后只操作副本；
   2. 用数据密钥解封 MK，打开数据库，执行完整性检查；
   3. 生成新的 K_dev，用新登录密码重建密码槽，原子写入 `keystore.json`；
   4. 本机已有数据目录时，先改名为 `data.replaced-<时间戳>` 保留，再把副本改名为正式目录。
3. 任一步失败则删除副本，保持本机原状。

### 8.6 备份与恢复

- 备份：在持有读事务期间对 `vault.db` 做文件级拷贝（单进程、单文件日志模式下结果一致），同时拷贝 `keystore.json`；拷贝后用 K_db 打开备份做一次完整性检查，通过才计为有效备份。所选数据库库自带的在线备份接口是否保持加密，M0 验证后择优使用。
- `keystore.json` 的每次改写：写临时文件 → 刷盘 → 原子替换，并保留上一版为 `keystore.prev.json`。
- 恢复：先把当前数据做一份备份，再替换；数据格式低于当前版本时随后执行升级脚本。
- 清理：超过保留份数时删除最旧的；升级前备份单独计数，至少保留最近 2 份。

### 8.7 剪贴板

- 主进程写入剪贴板并记下内容的哈希；定时器到点后，仅当剪贴板当前内容的哈希与之相同才清空。
- 程序锁定或退出时，如果剪贴板里仍是本程序复制的密码，立即清空。
- 排除 Windows 剪贴板历史需要设置特殊的剪贴板格式，Electron 没有直接接口，M0 验证可行性。

### 8.8 自动锁定

- 空闲检测用 `powerMonitor.getSystemIdleTime()` 轮询。
- `powerMonitor` 的 `lock-screen`、`suspend` 事件触发立即锁定。
- 锁定顺序：通知界面保存草稿 → 关闭数据库 → 密钥清零 → 切换到登录页。

## 10. 发布与更新

### 10.1 版本号

语义化版本 `主.次.修订`。数据格式有变化时至少升次版本号，并在更新说明里注明。

### 10.2 发布流程

推荐用 GitHub Actions，在打标签时自动构建并发布，办公电脑上不需要保存发布令牌：

1. 修改 `package.json` 的版本号，更新 `CHANGELOG.md`，提交。
2. 打标签并推送：`git tag v1.0.0`，`git push --tags`。
3. Actions（Windows 运行器）执行：安装依赖 → 类型检查与测试 → 构建 → 打包并上传到 GitHub Release（草稿状态）。
4. 人工检查草稿里的三个文件齐全，在发布说明里补上安装包的 SHA-256，然后点击发布。**只有已发布的 Release 才会被在线更新发现。**

备选：本机执行 `npm run dist`，在 GitHub 网页上手工创建 Release 并上传 9.3 节的三个文件。

如果采用“源码仓库私有 + 发布仓库公开”（设计文档第 8 章第 6 项的推荐），Actions 需要一个只对发布仓库有写权限的令牌，存放在源码仓库的 Secrets 里。

### 10.3 在线更新的实现

- `autoDownload = false`、`autoInstallOnAppQuit = false`、`allowDowngrade = false`，下载和安装都由用户确认。
- 把 `update-available`、`download-progress`、`update-downloaded`、`error` 等事件转成统一的 `update:status` 推给界面。
- 检查更新设 10 秒超时。自动检查的失败只写日志。
- 调用安装前：锁定密码库（关闭数据库）→ 备份 → `quitAndInstall()`。
- 网络走系统代理；设置里可改为不使用代理或手动指定。
- 未做代码签名时，更新器只校验 SHA-512，不校验发布者。

### 10.4 手动更新的实现

`update:installFromFile`：

1. 确认所选文件是 exe，读取其版本号（优先读文件版本资源，读不到则按文件名 `PwVault-Setup-x.y.z.exe` 解析），要求高于当前版本。
2. 计算 SHA-256 并显示，供用户与发布说明核对；同目录下如有 `latest.yml` 则自动比对其中的 SHA-512。
3. 用户确认后：锁定 → 备份 → 启动安装程序 → 退出本程序。

### 10.5 更新源的扩展

更新源在实现上就是更新器的一份配置：GitHub 源是 `{ provider: 'github', owner, repo }`，内网源是 `{ provider: 'generic', url }`。v1.1 增加 Nginx 时，只需在设置里保存地址并切换配置，发布文件与 GitHub 完全相同，放到 Nginx 静态目录即可。

免安装版不能使用更新器的自动安装，改为调用 GitHub 的“最新发布”接口比较版本号，有新版本时提示并打开下载页。

## 11. 测试计划

### 11.1 单元测试（Vitest）

| 模块 | 重点 |
| --- | --- |
| `crypto/kdf`、`crypto/aead` | 用公开的标准测试向量验证 Argon2id、HKDF、AES-GCM；密文或附加数据被改动时必须解封失败 |
| `crypto/keystore` | 初始化 → 解锁 → 改密码 → 换数据密钥的完整往返；旧密码、旧数据密钥失效；文件被篡改时解封失败；写入中断不损坏原文件 |
| `crypto/datakey` | 编码解码往返；单字符错误能被 CRC 发现；空格、连字符、大小写、易混淆字符的容错 |
| `vault/*` | 目录重名约束、移动成环检测、删除非空目录、回收站恢复到原目录 |
| `vault/search` | 中文、英文、1–2 个字的短词、多词组合、特殊字符；密码字段不可被搜到；回收站内容不出现 |
| `export/markdown` | 表格转义、多行字段、文件名净化与重名、遮蔽与明文两种模式 |
| `migrate/import` | 数据密钥错误、数据库损坏、格式版本过高时都能完整回滚 |

### 11.2 端到端测试（Playwright）

首次初始化、登录与锁定、条目增删改查、检索并复制、Markdown 编辑、导出、设置修改。

### 11.3 必须人工做的验证

| 场景 | 做法 | 通过标准 |
| --- | --- | --- |
| 迁移 | 把数据目录拷到另一台电脑或另一个 Windows 账户 | 只输登录密码打不开；输入数据密钥后数据完整 |
| 在线更新 | 在测试仓库先后发布两个版本 | 低版本能发现、下载、安装高版本，数据不变 |
| 手动更新 | 用高版本安装包覆盖安装 | 数据不变；用低版本安装包时被拒绝 |
| 卸载重装 | 卸载后重新安装 | 数据仍在，可直接登录 |
| 自动锁定 | 空闲超时、Win+L、休眠 | 均回到登录页 |
| 防截屏 | 系统截图、会议软件共享窗口 | 窗口内容不可见 |
| 明文不落盘 | 用十六进制工具搜索数据目录 | 搜不到任何已知的标题、用户名、密码 |

### 11.4 验收对照

每条原始需求（设计文档 2.1 节的 R-01 至 R-16，其中 R-02、R-15 归入 v1.1）在发布 v1.0 前逐条演示并打勾，清单随发布说明存档。

## 13. 开发规范

### 13.1 安全红线（代码评审时逐条检查）

1. 界面进程不得持有主密钥、数据库密钥或数据库句柄。
2. 不得关闭 `contextIsolation`、`sandbox`、`webSecurity`，不得开启 `nodeIntegration`。
3. 日志、错误信息、崩溃报告中不得出现字段值、密码、密钥。
4. 不得把明文数据写入临时文件（Markdown 导出是用户明确要求的例外）。
5. SQL 一律参数化，不拼接字符串。
6. 除更新检查外不发起任何网络请求；不加入统计、遥测。
7. 不自行发明加密算法或协议；`keystore.json` 结构的任何改动都必须提升 `format`、提供升级路径并补充测试。
8. Markdown 渲染结果必须经过净化后才能插入页面。

### 13.2 一般约定

- TypeScript 开启 strict；IPC 契约类型放在 `shared/`，两端共用。
- 主进程依赖尽量少，新增依赖需说明理由；用 `package-lock.json` 锁定版本，流水线中执行依赖漏洞检查。
- 提交信息采用“类型: 描述”的格式（`feat` / `fix` / `docs` / `refactor` / `test` / `chore`）。
- 影响数据格式、密钥体系或更新流程的改动，先更新设计文档再改代码。
